# 멱등 정책 (Sender)

## 무엇을 막는가
SQS Standard 큐와 Lambda 이벤트 소스 매핑은 at-least-once 로 전달한다. 같은 업무 요청이 두 번 이상 소비될 수 있다는 전제는 바꾸지 않는다. 목표는 **발송사가 받은 발송이 키마다 1번으로 수렴하는 것**이고, 아래 "남는 위험"까지 포함해 어디까지 보장되는지 적어 둔다.

## 키 범위
`idempotencyKey = tenantId:campaignId:recipientId:channel`
- 이 실습의 업무 규칙("같은 캠페인에서 같은 수신자에게 같은 채널로 두 번 보내지 않는다")에 맞춘 선택이다. 재발송을 허용하는 시스템이면 범위가 달라진다.
- SQS `MessageId` 는 쓰지 않는다. 같은 요청이 다시 발행되거나 DLQ 에서 재처리되면 새 MessageId 가 붙는다.

## 상태와 전이
| 상태 | 뜻 | 들어오는 조건 |
|---|---|---|
| (없음) | 처음 보는 키 | — |
| `IN_PROGRESS` | 누군가 선점해 발송 중 | 키가 없거나, `IN_PROGRESS` 인데 `leaseUntil` 이 지났을 때(한 번의 조건부 쓰기) |
| `COMPLETED` | 발송 끝 | 선점한 처리(owner 일치)가 발송을 마쳤을 때 |

처리 순서: 메시지 검증 → payload 확인 → 선점 → 발송사 결과 조회 → 발송 → `COMPLETED`.
- 선점 결과가 `COMPLETED` 면 건너뛴다(`SKIPPED_DUPLICATE`).
- 다른 처리가 선점 중이고 선점이 유효하면 보내지 않고 실패로 돌려 나중에 다시 받는다(`IN_PROGRESS_ELSEWHERE`).
- 발송이 실패하면 자기 선점만 지운다.

## 선점 만료
- `leaseUntil` = 선점 시각 + 30초. 함수 제한 시간(15초)보다 길게 둬서 살아 있는 처리의 선점을 빼앗지 않는다.
- 선점 뒤 함수가 중단되면 키가 `IN_PROGRESS` 로 남는다. 만료가 지나면 다음 재전달이 다시 선점해 보낸다(`IdempotencyRecoveryTest`: 즉시 재전달은 보내지 않고, 2초 만료 뒤 1번 보냄).
- 키 보관 기간(TTL `expiresAt`) 7일은 SQS 기본 메시지 보존 기간(4일)보다 길게 둔다.

## 발송사 측 멱등 키와 결과 조회
조건부 쓰기만으로는 "발송사는 처리했는데 응답이 타임아웃된" 경우를 막지 못한다. 선점을 풀고 재시도하면 다시 보낸다(`IdempotencyRecoveryTest`: 결과 조회 없이 2번).
- 발송 요청에 `idempotencyKey` 를 함께 보내고, 재시도 때 발송 전에 발송사에 이 키로 접수된 발송이 있는지 조회한다. 있으면 다시 보내지 않고 `COMPLETED` 로 기록한다(`RECOVERED_FROM_VENDOR`, 같은 테스트에서 1번).
- 이 실습의 모의 발송사는 결과 원장의 `by-idempotency-key` 인덱스로 조회한다. 실제 발송사는 멱등 키 헤더나 결과 조회 API 지원 여부가 다르다. 둘 다 없으면 이 위험은 남는다.

## 어디까지 보장되는가
| 경우 | 결과 |
|---|---|
| 같은 키가 차례로 다시 옴 | 1번 (`COMPLETED` 확인) |
| 같은 키가 동시에 옴 | 1번 (조건부 쓰기, 늦은 쪽은 나중에 다시 받음) |
| 선점 뒤 함수 중단 | 선점 만료 뒤 1번. 만료 전까지는 지연된다 |
| 발송사 처리 후 응답 타임아웃 | 결과 조회가 있으면 1번, 없으면 2번 가능 |
| 발송 성공 직후 `COMPLETED` 기록 전 중단 | 결과 조회가 있으면 1번, 없으면 만료 뒤 2번 가능 |
