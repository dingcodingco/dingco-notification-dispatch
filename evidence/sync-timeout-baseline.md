# 동기 baseline timeout 증거

환경: LocalStack 4.9 (로컬), 저장소 `main` 브랜치. 실AWS 미검증.
원본 출력: 교재 작업 폴더 `assets/raw/s2-*.txt`
조건: 모의 발송사 지연 20ms, 속도 제한 없음, k6 클라이언트 timeout 10초(`perf/k6/sync-baseline.js`)

## 측정 (2-3)
| 수신자 | 클라이언트 결과 | 응답 시간 |
|---:|---|---:|
| 10 | 200 | 254ms |
| 100 | 200 | 2,555ms |
| 300 | 200 | 7,683ms |
| 600 | timeout | 10,003ms |

## timeout 뒤 서버 쪽 (2-4)
- API 로그: `baseline-600 recipients=600 sent=600 elapsedMs=15004` — 클라이언트가 끊긴 뒤에도 15초에 600건을 모두 보냈다.
- 발송사 `accepted=1010` (= 10 + 100 + 300 + 600)

## 해석
- 응답 시간이 수신자 수에 비례한다. 요청 하나가 발송 전체를 붙잡는 구조다.
- timeout 을 받은 클라이언트는 발송이 됐는지 알 수 없다. 다시 보내면 600건이 중복된다.
- 그래서 접수와 발송을 나누고(Section 3·4), 재시도에 대비한 멱등 키가 필요하다(Section 6).
