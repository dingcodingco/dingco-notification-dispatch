# 발송사 429 제어 전후 증거

환경: LocalStack 4.9 (로컬), 저장소 `main` 브랜치. 실AWS 미검증.
원본 출력: 교재 작업 폴더 `assets/raw/s5-*.txt`
조건: 모의 발송사 한도 초당 2건(1초 고정 창), 지연 20ms, 수신자 60명, 배치 5

## 전후 비교 (5-2 → 5-4)
| 항목 | 제어 전 (`VENDOR_MAX_RPS=0`) | 제어 후 (`VENDOR_MAX_RPS=2`) |
|---|---:|---:|
| 발송사 429 | 26 | 0 |
| 발송사 최대 초당 요청 | 5 | 2 |
| 완료 시간 | 약 82초 | 약 60초 |
| 다시 받은 메시지 | 22건(최대 3회 수신) | 0건 |

## 해석
- 429 는 호출 안에서 재시도하지 않는다. 메시지가 실패로 보고되고 가시성 타임아웃(20초) 뒤 재전달로 다시 시도한다.
- 제어 전 최대 수신 3회는 `maxReceiveCount=3` 과 같다. 한도가 더 낮거나 양이 더 많으면 정상 메시지가 DLQ 로 갈 수 있다.
- 보내는 쪽에서 속도를 맞추자 재전달이 사라졌고 전체 시간도 줄었다.

## 동시 실행 상한 (5-1)
- `SENDER_MAX_CONCURRENCY=2` → 이벤트 소스 매핑 `ScalingConfig.MaximumConcurrency: 2` 설정 확인
- LocalStack 4.9 는 이 상한을 강제하지 않는다. 동시 실행 수의 변화는 실제 AWS 에서 측정한다.

## 처리량 예산 (5-3, `scripts/measure/budget.py`)
- 동시 실행 상한 = 발송사 한도 ÷ 인스턴스당 속도
- 1억 건 계산 예(발송사 500/초, 인스턴스당 10/초는 가정값): 상한 50, 200,000초 ≈ 55.6시간 ≈ 2.3일
